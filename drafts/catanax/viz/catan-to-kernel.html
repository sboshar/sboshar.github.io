Catan on a GPU

How a board game became thousands of copies running at once, and why the hard part was working out who has the longest road.

AuthorSam Boshar
Projectcatanax
StatusDraft

I've been training agents to play Catan by self-play, the way AlphaZero learned Go. The idea is simple to state and expensive to run. The agent plays itself millions of times, and before every move it runs a small search that tries the moves it's considering on copies of the game. Each of those tries is a call into the game engine, so the engine's speed sets the speed of everything else.

catanatron is the careful, standard Python implementation of Catan. On 16 CPU cores it plays about a hundred games a second. That's fine for evaluating a bot and far too slow for self-play at the scale I wanted. (I train on two rule sets: catanatron's, two players racing to 10 points, and colonist.io's 1v1 rules, first to 15, with dice that remember recent rolls. Both come up below.)

The usual way out is to put the games on a GPU. JAX, a Python library that compiles array code for accelerators through a compiler called XLA, has a function called vmap: you write the rules for one game, as a pure function on arrays of fixed size, and vmap runs it on thousands of games at once. That gets you a long way. It also hides a problem that most of this page is about. vmap runs every game in lockstep, so when one game has more work to do than the rest, the rest wait for it, and Catan has one rule that does exactly this.

This page is about how that wait went away, and what came after it. For the colonist recipe I train most, a training run that would take 153 hours on a plain JAX engine now takes about two. Almost every step of the way came down to asking two questions of each piece of work: does its cost depend on the slowest game in the batch, and can its result change anything at all?

The answer to the first question was to stop writing the engine for a batch and write it for one game, as a GPU kernel, the unit of code a GPU launches, that runs one small program per game. The first half of the page follows a move through that engine and then the rule that dominated its cost. The last two sections move up to the search that calls the engine, where the second question turned out to matter just as much.

The board as arrays

To a person, a Catan board is geometry: hexes, the corners where they meet, and the edges between corners. The engine needs none of the geometry, only what touches what. A board has 19 hexes, 54 corners and 72 edges, and a few small fixed tables record which corners surround each hex and which two corners each edge joins. With those tables, rules become lookups. "No settlement next to another settlement" turns into: look up the corner's neighbours and check whether any of them is occupied.

Everything that changes during a game fits in 46 arrays of fixed size: who owns each corner and edge, each player's hand, the development card deck, the dice history, and so on. That's about 465 integers. For the kernels, I pack them into one row of 512 integers, rounded up to a power of two because the kernel compiler wants one, which comes to 2 KB per game. One move inside the kernel

A move arrives as a single number. The network chooses among 294 actions, laid out in blocks: one block for a settlement on each corner, one for a road on each edge, and so on. Playing a move means finding the block the number falls in, running that rule, and updating every part of the state it touches. A settlement, for instance, pays four resources to the bank, adds a victory point, and can cut an opponent's road in two.

My first GPU engine did this with vmap over a switch statement, one branch per kind of move. It was slow, and for a simple reason. A switch inside vmap can't actually branch, because each game in the batch wants a different branch, so XLA runs all thirteen branches for every game and keeps one result. Twelve of the thirteen branches' work is thrown away.

The version that worked is a Pallas kernel that runs one small program per game. Pallas is JAX's way of writing your own GPU kernel; on NVIDIA GPUs it compiles through Triton, whose restrictions come up later. Each program reads its game's row, takes the one branch it needs, and writes the row back, all in one launch. Step through Figure 2, where Blue builds a settlement that cuts Orange's road. At the dispatch step, the toggle shows what the vmap version does instead.

What the GPU is doing

Why doesn't one program per game run into the same lockstep problem as vmap? The answer is in how the GPU runs it. Each program runs as a single warp, 32 threads that execute each instruction together. (That isn't Triton's default; the next section is about why it has to be one.) Inside a program, an if is a real branch, because the whole warp is working on one game and agrees on which way to go. Two games taking different branches cost nothing extra, because they're different warps.

An A100 has 108 streaming multiprocessors (SMs), and each can hold up to 32 one-warp programs at once. That's up to 3,456 games in flight, so a batch of 4,096 runs in a little over one wave, and when a game finishes, its slot goes to the next game waiting. The whole batch is 8 MB of state, small enough to stay in the A100's 40 MB L2 cache. Figure 3 animates one step.

A race between warps

Triton compiles a Pallas program to four warps by default. The engine code is scalar: it describes one game, so every thread does the same work, including the same read-modify-write on the same address. Take a counter that holds 5 and should become 6. Within one warp that's harmless, because all 32 threads read 5 together and all write 6. Separate warps, though, are scheduled independently. If three warps have already written 6 before the fourth does its read, the fourth reads 6, adds one, and writes 7.

In the engine kernel this corrupted about 11 games out of 4,096, different ones on every run. It never appeared at the small batch sizes I used while developing, only at the size I trained with. The fix is to run each program as a single warp. For a kernel that updates memory in place, the warp count is a correctness setting, and the default is the wrong one.

Longest road

Most of Catan's rules are cheap: a few lookups and some arithmetic. One isn't. The longest road card goes to the player with the longest continuous trail of roads, at least five long, that never uses a road twice and never passes through an opponent's settlement. Finding that trail is a search. On one straight road it's trivial. On a network with branches and loops, the number of trails to try grows quickly.

On average the search is cheap. The trouble is the spread: in one batch the average board needed 73 steps of the search and the worst needed 796, more than ten times as many. Under vmap, a loop like this runs in lockstep. The batch keeps iterating until its slowest board is done, so every game pays for 796 steps, and less than a tenth of that time is useful work. When I profiled the vmap engine, longest road was about 85% of the time per move.

I tried cheaper fixes first. Because vmap runs every branch of the switch, the search was running three times per step, once in each branch that could change a road; running it once instead made the whole step 2.8× faster. Searching only from a newly built road helped the usual case (more on that idea below). I also tried a closed-form count based on how many roads meet at each corner, and found networks where it overcounts, so it could never be exact. None of these touched the real problem: the batch still waited for its slowest board. Figure 5 shows what happens when it doesn't have to. Press Race.

In the real engine, moving the search into the kernel made longest road 9.5–12× faster, at batches of 16,384 and 32,768 games, with identical results on 73,728 test positions.

Writing it as a kernel meant living inside Triton's restrictions: no scatter, no indexing into a vector with a computed index, and every array a power of two long. The search is a depth-first search with an explicit stack. Each entry on the stack, a frame, is one partial trail: the corner it has reached, its length, and which roads it has used. Two tricks make it fit.

First, a frame packs into one 32-bit integer: 6 bits for the corner (54 corners fit in 64), 5 for the length, and 16 for which of the player's road slots are used (a player owns at most 15 roads). So the whole stack is a vector of 32 integers. Second, the push. Popping a frame produces a few candidate extensions, and each valid one should land in the next free slot. Normally you'd compute each candidate's slot and scatter it there, but Triton has no scatter, so the push runs backwards: each of the 32 slots compares every candidate's target position with its own index and copies the one that matches. Searching only what changed

With the kernel in place I profiled again. Late in the game, longest road was back at about 85% of the time, the same share it had under vmap. This was the lockstep problem again, in a new form. Figure 5's fix only helps when there's a queue of games waiting to take a freed slot. The profile used 1,024 games, which fit on the A100 all at once, so there was no queue: games that finished early left their slots empty, and the launch still took as long as its slowest game. The slowest game was whichever one had just built a road onto the biggest network, and on every road build the kernel searched that whole network from scratch.

It didn't need to. A new road can only create trails that run through it; every other trail existed before. So the new longest road is the larger of the old one and the longest trail through the new road, and only a settlement that cuts a road needs a full search. My XLA engine already worked this way. When I wrote the kernel, I had ported the full search instead.

A trail through the new road extends from both of its ends. The search grows the trail from one end, then switches once and grows it from the other, never reusing a road. Switching exactly once keeps it from counting the same trail several times. Figure 7 steps through it on Orange joining its two chains.

That still does more sequential work than it should. For every way of extending the first end, it explores every way of extending the second again, so its work grows like the product of the two. But the two ends only interact through one question: do they use the same road?

So the current kernel splits the work. Call each trail grown outward from one end an arm. The kernel lists every arm from each end once, into two lists of up to 32, storing each arm as its length and a bitmask of the roads it uses. Two arms join into a valid trail exactly when their masks share no bit, which is one bitwise AND. If one end has 5 arms and the other has 4, the old search walked about 5 × 4 combinations one after another; the new one walks 5 + 4 arms and then tests all 20 pairs at once. Even the full 32 × 32 grid is one vectorized pass over the warp's 32 threads: ANDs to find pairs that share a road, then a maximum over the pairs that don't.

One rule needs care. Like catanatron, the search never steps onto a corner held by an opponent, but a trail may start at one. So only one end of a trail can sit on an opponent's settlement, and two arms that both end on one don't pair.

The board's shape keeps the lists short. Every corner has at most three roads, and one of them is the road a trail arrived on, so a trail branches at most two ways at each step. In real self-play no end ever had more than 21 arms, comfortably under 32. If a list did overflow, the kernel would fall back to the old search, so the answer is always exact. Hover over a cell in Figure 8 to see the trail it stands for.

On real self-play road builds, pairing the arms cut the average search from 11.4 steps (the search of Figure 7) to 7.2, and the worst game's from 134 to 38. The full search now runs only when a settlement cuts a road. The kernel matched the reference engine on every test, including 196,608 games forced to build a road or a settlement.

The whole engine step

The same profiles pointed at one more piece still written in plain XLA: the mask of legal moves, which the network needs before every search. It compiled to 27 separate GPU kernels, all to do a few dozen comparisons per game. Rewritten as one Pallas program per game, it's about five times faster.

How much did all of this buy? Figure 9 times one step at four points in a game.

Searching only through the new road makes the engine step 1.9× faster late in the game. With the faster mask on top, the whole simulation step is 1.5–2.2× faster than before at every stage of a game, and 5–9× faster than plain XLA.

Figure 10 splits a step into its parts, before and after. The legal-move mask goes from about half of the step to a tenth, and longest road nearly disappears, except in the largest late-game networks. The biggest piece left is, of all things, drawing random numbers for dice rolls and steals, which still happens in plain XLA before the kernel runs.

Skipping work that can't matter

Once the engine was fast, the bottleneck moved up to the search that calls it. For each position, self-play builds its training target with a one-ply search. It takes the 16 moves the network rates highest, plays each one on a copy of the game, and asks the network how good each resulting position is. Those 16 values, blended with the network's own preferences, become the target the network learns from, and the move actually played is sampled from that target. With 2,048 games in a batch, that's 32,768 positions to step and evaluate per move, and evaluating them was the largest single cost in self-play.

This is where the second question from the start of the page comes in. A program with fixed shapes does work for every slot, whether or not that work can matter, and many of those 16 values can't. If a position has fewer than 16 legal moves, the extra slots are padding. If it has only one legal move, which in Catan is common (rolling the dice, ending a turn), the target is that move with probability 1 whatever the values say. And when rolling is one of several options, the search doesn't trust a single random roll: it replaces that slot's value with an exact average over the 11 dice totals, so the network's evaluation of the one roll in the slot is never used. Measured on real self-play, only 21% of the slots matter in colonist, and 35% in catanatron. In colonist, about four of every five evaluations were wasted.

The obvious fix is to evaluate only those. The catch is that a compiled JAX program has fixed shapes; it can't call the network on however many rows happen to matter this step. The standard way around this is packing, also called stream compaction. Set aside a buffer smaller than the batch. Number the slots that matter 0, 1, 2 and so on with a prefix sum, which is just a running count. Copy each one into its buffer row, fill any leftover rows with harmless copies, evaluate the buffer, and write each result back to the slot it came from. If more slots matter than the buffer holds, run it again on the rest. The answer doesn't change; overflowing only costs another round.

At full scale it looks the same with more cells. Figure 12 packs 32 games of 16 candidates each, drawn to match the fractions measured in self-play, into a buffer of 40% of the slots.

The 40% came from measurement: colonist needs 21.5% of the slots on average and 25% at most, catanatron 35% and 38% at most. At 30%, catanatron overflowed into a second pass on most steps, and at 10% the extra passes cost more than they saved. Packing took self-play from 832 to 1,307 games a second on colonist, and from 3,057 to 4,166 on catanatron.

Same input, different output

Packing changes one thing the engine never touched: the shape of the batch the network sees. It should change nothing else, so I compared packed and unpacked self-play directly. A quarter of the policy targets were different. I traced it to the network itself. In that test one packed buffer held 204 positions, and the same 204 positions evaluated on their own, and as the first 204 rows of a 512-row batch, gave values that differed by 0.018, on a value that runs from −1 to 1. That's several times the rounding error of one matrix multiply in bf16, the 16-bit format the network computes in, which keeps only about three significant digits. At first I didn't believe it was rounding at all.

It was rounding, compounded. A GPU matrix multiply is split into output tiles, and the SMs work on tiles in parallel. With a few hundred rows there aren't enough tiles to keep 108 SMs busy, so XLA also splits each 256-long dot product into four pieces of 64, which different SMs can work on, and adds the partial sums in fp32. On that path it never rounds the layer's output back to bf16. At 512 rows there are enough tiles, so XLA uses a single matrix multiply, which does round. Either way the value is correct to bf16 precision, but the two can differ by up to half a unit in the last place, in every element of every layer, and the residual connections carry that forward and add to it.

Where does 0.018 come from? Figure 13 follows the difference through the network, layer by layer.

The difference starts at exactly half a unit in the last place after the first layer and grows to 0.018 at the value. The search's target adds 50 times the value to the network's logits, so 0.018 becomes 0.9, most of a logit, which is enough to reorder close moves. The obvious switches don't help. XLA's deterministic mode makes one shape repeatable but doesn't make two shapes agree, and running the network in fp32 removes most of the gap but not all of it, because the four partial sums are still added in a different order. With the splitting pass turned off, every layer matches exactly at every batch size of 128 rows or more.

Fixing that uncovered two smaller cases of the same thing. On colonist, XLA computed the value head's tanh twice, once in the normal place and again inside another fused kernel, and the two implementations can disagree in the last bit. That would normally be harmless, but colonist rescales values per position, and that magnified the one-bit difference about a thousandfold. Separately, with fewer than about 120 rows, XLA sums the normalization layers in a different order.

The fixes were to turn off the splitting pass when compiling self-play (training keeps it, because it needs it), to put an optimization barrier on the value output so it's computed once, and never to pack fewer than 128 rows. After that, packed and unpacked self-play agree bit for bit.

The unpacked code, it turned out, had never been batch-invariant either. Searching 16 games on their own, instead of as part of a batch of 64, changed its policy targets by up to 0.10. Nothing in the original code was wrong; the same rounding had just never been looked at.

Where this leaves things

The bottleneck moved four times: from the switch statement, to longest road, to the legal-move mask, to the search's calls into the network. Each fix answered one of the two questions this page started with.

What's left is mostly not in the engine. Most of a self-play step is now the network, and more than half of the positions that colonist self-play searches have only one legal move. Playing those moves inside the engine kernel, instead of searching them, is the experiment I'm running next. Speed roughly doubles. What I don't know yet is whether the agent learns as well when those positions are no longer part of its training data.
