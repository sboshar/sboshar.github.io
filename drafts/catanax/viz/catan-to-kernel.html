Catan on a GPU

How a hex board becomes a 512-integer row, what a single move does inside a Pallas kernel, and why the hardest part was a road.

AuthorSam Boshar
Projectcatanax
StatusInteractive draft

Self-play reinforcement learning is a throughput game. AlphaZero-style training plays millions of games, and every move runs a search that steps the environment many more times. catanatron, a careful Python engine, manages about a hundred games per second. To go faster, catanax rewrites Catan as a pure function over fixed-shape integer arrays, so thousands of games can step at once on a GPU.

This page follows one game through that pipeline: from the board, to the memory layout, to one move inside a fused kernel, to the hardware that runs it.

1The board is just indices

A Catan board looks like geometry, but the engine only needs incidence: which intersections touch which hex, and which road slots connect which intersections. There are 19 tiles, 54 nodes and 72 edges. Their relationships fit in a few tiny static tables, so every rule becomes a gather. For example, the distance rule ("no settlement next to another settlement") is occupied[NODE_NEIGHBORS[n]].any().

The game's mutable state is 46 fixed-shape arrays, about 465 integers. For the kernels they're packed into a single row, padded to 512 values (2 KB). Hover over the board or the row to see how they correspond.

2One move, one kernel launch

The policy picks one of 294 flat action ids. Applying it means decoding the id, running the matching rule, and updating every field it touches. In the first version of the engine this was a jax.vmap over a 13-way lax.switch. Under vmap, a switch whose branch differs per game can't actually branch, so every game evaluated all 13 action families and threw 12 results away.

The Pallas version runs one program per game. A whole move — the applier, the road-cut connectivity check, the longest-road search and the winner check — happens in a single launch that reads and writes this game's row in place. Step through Blue building a settlement that cuts Orange's road:

3The hardest part was a road

Longest road awards 2 VP to whoever owns the longest trail of connected roads (at least 5) that doesn't reuse an edge and doesn't pass through an opponent's building. Computing it exactly is a search over trails, and its cost depends entirely on the shape of the road network. A straight line is trivial; a tangle with branches and loops explodes.

That variance is what made it expensive. Profiling the vmapped engine showed longest road taking about 85% of step time. The search itself isn't slow. The problem is that a vmapped while_loop runs in lockstep: the batch keeps iterating until its slowest board finishes. Average cost was 73 node visits; the worst board in a batch took 796.

Several things were tried before the kernel. Running the search once per step instead of once per switch branch gave 2.8×. Updating incrementally (a new road can only extend trails through itself, so you only search from that edge) helped the common case. A closed-form formula based on node degree parity was attempted and provably over-counts. But a road cut, like the one in Figure 2, still needs a full search.

The kernel version had to work within Triton's limits: no scatter, no dynamic indexing into register vectors, power-of-two shapes. Its trick is that a whole DFS frame fits in one 32-bit integer: 6 bits of node, 5 bits of path length, and 16 bits of "which of my roads have I used" (a player owns at most 15). The stack is a vector of 32 such integers. A push can't be written as a scatter, so it's inverted: each stack slot pulls the candidate whose target position equals its own index.

4Search only through the new road

Profiling the fused kernel showed longest road eating about 85% of a late-game launch again. At batch 1,024 every game fits on the A100 in a single wave, so the launch takes as long as its slowest game, and that is whichever game just built a road onto the biggest network. The kernel was running the full search from every node of that network on every road build.

It didn't need to. Building a road can only create trails that use the new road: every other trail existed before. So the new longest road is max(old length, longest trail through the new edge), and only a settlement that cuts a road needs a full recompute. The reference engine already did this (catan._longest_trail_through); the fast kernel was using the slow algorithm.

The new road can sit in the middle of the longest trail, so the search grows two arms, one from each end of the edge, without reusing a road. Ported into the Pallas kernel, with the full search kept only for road cuts, it was bit-exact on every parity test and on 196,608 games forced to build a road or a settlement. The same profiling also pointed at the legal-action mask, still plain XLA: 27 separate GPU kernels for a few dozen comparisons per game, a flat 0.1 ms per batch. Rewritten as one Pallas program per game (one vector over the 294 action ids, gathering straight from the state row), it is about 5× faster and also bit-exact.

5What the A100 is actually doing

With one program per game, each game runs as a single warp: 32 threads executing the same scalar engine code. Branches inside a program are real, because the whole warp agrees on which action it's applying. Different games taking different branches costs nothing, because that divergence is between warps, not within one.

An A100 has 108 streaming multiprocessors (SMs). Ampere allows at most 32 resident blocks per SM, so with one-warp blocks about 3,456 games are in flight at once, and a 4,096-game batch runs in about 1.2 waves. The batch's entire state is 4,096 × 2 KB = 8 MB, which fits in the 40 MB L2 cache.

6The bug that only appeared at batch 4,096

A Pallas program on Triton compiles to num_warps × 32 threads, with a default of four warps. Engine code is scalar, so every thread redundantly performs the same load, add and store to the same address. Within one warp that happens in lockstep and is harmless. But warps are scheduled independently. A lagging warp can load a value a faster warp has already incremented, and write back a doubled result.

In the engine kernel this corrupted about 11 of 4,096 games, different ones on every run, and never showed up at the batch sizes used during development. The fix, num_warps=1, is a correctness requirement for any kernel that updates memory in place.
